**Goal:** Match vanilla on recipe matching and result stacks on both Java Edition 1.8.9 and 26.1.2, in the 2x2 player grid and the 3x3 table, including shift-crafting.

**Architecture:** Both versions ship a complete recipe registry in generated data — `generated/java/v1_8/recipes.go` and `generated/java/v26_1/recipes.go`, neither an alias — and `data.Recipe` already models both shapes a recipe can have: `Ingredients` for shapeless and `InShape` for shaped. So the matcher is a pure function from a grid to a recipe, and the two versions differ in exactly one way that matters: **1.8.9 ingredients carry a metadata variant and 26.1.2's do not**, because the flattening moved variants into distinct item IDs. The generated 26.1 file says so in its own header. The matcher is shared; ingredient equality is version-owned.

**Tech Stack:** Go 1.26.6 from `openserbia/go-flake`, Devbox, Task, `minecraft-protocol`'s generated recipe and item data, `headless-minecraft`'s `world`, `event`, and `client`, `relay`'s capture oracle, and pinned vanilla 1.8.9 and 26.1.2 servers.

### What reconciliation changed

Three things, and one of this plan's central claims got a number behind it
rather than a correction.

- **The click action is `version.ActionClickSlot`.** M9.7 named it
  `client.ActionClickSlot`; the interaction primitives plan builds it in
  `version` as `{Window uint8, Slot int16, Button uint8, Mode ClickMode,
  Transaction int16}`, and M9.7's reconciliation moved to match. Task 4's tests
  are retyped.
- **`data.RecipeResult` carries `Metadata`.** This plan listed it as `{ID,
  Count}`. On 26.1 the field is there and unused; on 1.8.9 a result's metadata is
  what separates one wool from another, so a matcher that builds a result from
  `{ID, Count}` alone loses the variant on the version that has variants.
- **The gate does not live in `minecraft-simulation`.** That repository has no
  inventory and no recipe model — its packages are the kernel, the block world,
  and movement. Crafting is client state, so Task 5's corpus and gate move to
  `headless-minecraft`, beside the code they gate.

**The version-owned-equality claim is now measured, not argued.** Every
ingredient and result in `generated/java/v26_1/recipes.go` carries `Metadata:
-1` — 9,911 of 9,911 occurrences — while `generated/java/v1_8/recipes.go` uses
real values throughout, including 1,123 zeroes and hundreds each of 1 through
15. So a matcher that ignores metadata is right for 26.1 by accident and wrong
for 1.8.9 by construction, exactly as this plan said:

```bash

## Design decisions this plan settles

**Ingredient equality is the only version-owned part.** On 1.8.9 an ingredient
is an item ID and a metadata value, and `-1` means "any variant" — wool of any
colour crafts the same thing. On 26.1.2 the flattening moved variants into
distinct item IDs, and the generated file states it: "Java 26.1 recipe results
carry no metadata: the flattening moved variants into distinct item IDs, so a
result is an item and a count." A matcher that compares metadata on 26.1.2 is
comparing a field that is always `-1`, which happens to work; a matcher that
ignores metadata on 1.8.9 matches red wool against a blue-wool recipe, which
does not. Shared matcher, version-owned equality.

**A shaped recipe matches anywhere it fits in the grid, and that is most of the
difficulty.** A 2x2 recipe placed in the bottom-right of a 3x3 grid is the same
recipe. Vanilla slides the pattern across every offset that fits and requires
every other cell to be empty. A matcher that only tests the top-left offset is
right for the tutorial cases and wrong for most real ones — and it passes any
test suite written by someone who placed the ingredients neatly.

**Mirroring is a 1.8.9-era question that must be answered per version, not
assumed.** Vanilla mirrors some shaped recipes horizontally and not others.
Task 2 answers it from the corpus rather than from a rule this plan states,
because getting it wrong in either direction produces a matcher that crafts
things vanilla will not or refuses things it will — and both are silent.

**The 2x2 grid is not a smaller 3x3.** It is a different window with its own
slot indices, and a recipe wider or taller than two cells simply cannot match in
it. M3's session findings already asked whether M3's registry swap broke the 2x2
matcher; it did not, and the real defect was a shift-click handler that crafted
once instead of draining the grid. Both are fixed and tested. This stage
verifies against vanilla rather than re-litigating either, and the shift-craft
test lives here because this is the stage that owns crafting.

**Shift-crafting repeats until an input runs out, and the result count is the
thing to check.** It is the highest-value test in this stage because it
compounds three separate rules — matching, result stack size, and drain — so a
wrong result count localises the defect to one of them.

// Cell is one crafting grid cell. An empty cell has a zero ID.
type Cell struct {
    ID       data.ItemID
    Metadata data.Metadata
}

// Grid is a crafting grid, row-major.
//
// Width and Height are carried rather than inferred because a 2x2 grid is not
// a smaller 3x3: it is a different window with its own slot indices, and a
// recipe wider or taller than two cells cannot match in it at all.
type Grid struct {
    Width, Height int
    Cells         []Cell
}

// Trim returns the smallest sub-grid containing every non-empty cell, and its
// offset within the original.
//
// This is what makes offset matching tractable: rather than sliding a pattern
// across every position, trim the grid once and compare against the pattern
// directly. The offset comes back so a caller can tell where the match landed.
func (g Grid) Trim() (Grid, int, int)

// Ingredients decides whether a grid cell satisfies a recipe ingredient.
//
// It is version-owned because the two editions disagree about what an
// ingredient is. On 1.8.9 an ingredient is an item and a metadata variant, and
// -1 means any variant. On 26.1.2 the flattening moved variants into distinct
// item IDs and metadata is always -1, so comparing it is comparing a constant.
// A matcher that ignores metadata matches red wool against a blue-wool recipe
// on 1.8.9; one that compares it on 26.1.2 is merely doing nothing.
type Ingredients interface {
    Satisfies(cell Cell, want data.Ingredient) bool
}
```

## Risks

**Offset matching is the likeliest silent defect and the easiest to test
around.** Every hand-written test places ingredients in the top-left, because
that is how a person lays out a grid on paper. The offset test in Task 2 has to
be written deliberately or it will not exist.

**The recipe registries are large and the corpus is a sample.** Thousands of
recipes, two versions, two offsets each is not a runnable gate. Sampling is the
right call; sampling without logging what was dropped is what makes a sample
read as a sweep.

**A wrong inventory from M9.7 surfaces here as a crafting bug.** If M9.7's
rollback is wrong, a craft will fail for no visible reason and every instinct
will point at the matcher. Before debugging a crafting failure, check whether
the client and server agree about the grid contents — M9.7's server-comparison
helper exists for that and is worth reaching for first.

**Recipe-book state is out of scope.** 26.1.2 tracks which recipes a player has
unlocked and refuses some crafts on that basis; `container.recipes_changed`
already observes it and nothing here acts on it. Say so in the test file. A
craft refused for a locked recipe will otherwise look like a matcher defect, and
it is the one failure in this stage with an entirely different cause.
